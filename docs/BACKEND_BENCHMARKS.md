# Offline backend performance baseline

This is an explicit developer command, not application startup code. It exercises
the actual FastAPI application, routes, middleware, response validation, provider
services, TEI parser, caches and local inference through HTTPX's in-process
`ASGITransport`. Only outbound provider HTTP is replaced with `MockTransport`.
No production code, frontend code, dependencies or model artifacts are changed.

## Run from the repository root

Use the project's installed Python environment and committed lockfile. After the
normal `uv sync --project apps/api --locked --group dev` setup, the benchmark
itself can run with uv's network access disabled:

```bash
uv run --offline --project apps/api python apps/api/scripts/benchmark_api.py
```

The default run uses caller concurrency levels **1, 5 and 10**, a controlled
**10 ms delay per mocked provider request**, one cold wave and 30 warm requests
per scenario/level. It prints a terminal table. Optionally export JSON to a new
file (existing files are deliberately never overwritten):

```bash
uv run --offline --project apps/api python apps/api/scripts/benchmark_api.py --json /tmp/trace-backend-baseline.json
```

For a shorter run or a focused comparison:

```bash
uv run --offline --project apps/api python apps/api/scripts/benchmark_api.py --concurrency 1 5 --requests 10 --provider-delay-ms 25 --scenarios search neighbors health_under_load
```

All application settings are supplied explicitly. The benchmark does not use
backend `.env` settings or shell credentials. It uses a dummy provider key,
disables database connectivity and disables Semantic Scholar. The normal app
lifespan runs; its shared provider client is then replaced on this isolated app
instance before any benchmark requests. The real application/service code is not
patched. An import-time settings guard prevents `app.main`'s unused module-level
app from reading `.env` during standalone execution.

## Scenarios and evidence

| Scenario | Actual route | Input and behavior |
| --- | --- | --- |
| `health` | `GET /api/v1/health` | Standalone baseline; no provider requests |
| `search` | `GET /api/v1/papers/search` | Clearly labeled synthetic benchmark metadata |
| `neighbors` | `GET /api/v1/papers/W1/neighbors?limit=2` | Synthetic seed, one reference and one incoming citation; correct citing-to-cited direction |
| `classification` | `POST /api/v1/citation-contexts/classify` | Recorded BART → Word2Vec pair, exact existing OpenAlex metadata and `bart.xml`, real TEI verification/extraction and the existing local model |
| `health_under_load` | Health probes during held search requests | Waits until all background callers enter mocked provider HTTP, then holds them open while sending sequential health probes |

Synthetic metadata is in
`apps/api/tests/fixtures/performance/provider_responses.json`. These W1/W2/W3
records are test-only placeholders, not claims about real academic works, and
their text is never classified.

Classification reuses `apps/api/tests/fixtures/tei/works.json` and `bart.xml`,
whose attribution and capture provenance are in that directory's existing
`README.md`. It uses BART `W2982399380` citing Word2Vec `W1614298861`. No passage
or prediction is generated by the harness. The production parser extracts the
recorded genuine sentence and the production inference service predicts its
intent. `mode=live` bypasses bundled examples; with Semantic Scholar disabled,
the real coordinator exercises its OpenAlex TEI fallback and existing caches.
This deliberately excludes Semantic Scholar pacing, retries and the competing
provider race. It is not a provider-coverage benchmark.

By default the existing trusted artifact directory is `apps/api/artifacts`.
`--artifact-dir PATH` can select another **already trusted local** artifact pair;
joblib artifacts must never come from an untrusted source. Missing or incompatible
artifacts produce the real route's HTTP 503 `model_unavailable`, an explicit
unavailable count, and a failing run status. Other scenarios still run. No
artifact is downloaded, trained, replaced, or manufactured.

## Cold, warm and health overlap

Each scenario/concurrency combination gets a fresh app, service caches and
inference service. **Cold** is exactly one concurrent wave of N requests against
that fresh instance. Requests in the wave may share/coalesce retrieval and model
loading; it does not mean every request independently downloads/parses/loads.
**Warm** is `--requests` subsequent requests on that same instance with up to N
callers. An unsuccessful cold wave is marked `cache_precondition=not_established`
on the following batch instead of claiming a successful warm-up.

Search/neighbor routes currently have no response cache, so their warm provider
counts may equal their cold per-request counts. Classification can reuse the
existing retrieval caches, while still running actual inference each time. The
benchmark records observed behavior without adding or changing caches.

`health_under_load` is a separate diagnostic, not a cold/warm comparison. Its
reported `concurrency` is background search concurrency; `probe_concurrency` is
1. `overlap_verified` must be true, meaning **every health request started while
provider work was active**. `background_search` contains the background request
outcomes. Provider counts on this row belong to those background searches, not
to health itself. The gate is released and background tasks awaited even on
cancellation. This tests responsiveness during waiting provider I/O, not during
a CPU-saturating classification workload.

## Reading the measurements

- `request_count`: scheduled requests in a row. Completed, successful, errored
  and cancelled counts are separate. Background searches are a separate count.
- `median_ms`, `p95_ms`, `max_ms`: actual elapsed request-to-response times using
  `perf_counter`, including ASGI handling, validation/serialization, service
  queueing, controlled provider waits and inference. Harness result inspection is
  excluded. P95 uses the **nearest-rank** definition: sorted sample at
  `ceil(0.95 × sample_count)`. Cold waves have only 1/5/10 samples; their P95 is
  descriptive and statistically weak. Repeat runs and use larger warm batches
  for comparisons.
- Completed HTTP failures and request timeouts remain in the latency samples;
  fast failures must not be interpreted as successful optimization. Requests
  cancelled by a case deadline are counted but have no fabricated latency.
- `requests_per_second`: all completed attempts divided by batch wall time,
  including failures. Always interpret it alongside `success_count` and errors.
- `peak_in_flight`: observed API caller concurrency, not the number of tasks
  merely created. `provider_peak_in_flight` measures mocked HTTP overlap; graph
  expansion can issue multiple provider requests per caller.
- `provider_request_count` and `provider_requests_by_kind`: mocked HTTP attempts
  dispatched in that phase, including attempts later cancelled. The counters
  reset between phases; fixture preparation is not counted as HTTP.
- `classification_unavailable_count` includes missing-model errors and HTTP 200
  responses without a classified passage. `model_versions` comes from actual
  returned classifications. Reports contain no generated confidence scores.

JSON includes configuration, dependency/runtime versions and SHA-256 hashes of
the fixture files. `valid_run` distinguishes a completed controlled experiment
from a harness/network/deadline problem; it does not mean every request succeeded.
`all_requests_successful` also requires zero foreground/background errors and
verified health overlap. A controlled failure can be a valid measurement.

## Bounds, failures and isolation

- `--concurrency`: 1–6 unique levels, each between 1 and 20.
- `--requests`: highest selected concurrency through 200.
- `--provider-delay-ms`: 0–1000; `--provider-status 403` simulates provider rejection.
- Defaults: `--request-timeout-seconds 10`, `--case-timeout-seconds 30`,
  `--total-timeout-seconds 120`. Upper bounds are 60/120/300 seconds.
- Deadlines are cooperative asyncio deadlines. Already-running CPU/thread work
  cannot be forcibly stopped, and cleanup can extend wall time beyond a deadline.
- Exit **0**: valid run with all requests successful; **1**: valid measurement
  with request failures/unavailable classifications or failed overlap check;
  **2**: invalid configuration/run, blocked network/unknown provider request,
  or report-file write failure. Partial completed rows survive a total timeout.

Mock responses exist only for recognized fixture URLs. Unknown requests fail
closed; there is no live fallback. During execution, the standalone harness also
blocks real HTTPX transports, DNS resolution, and socket connects. Blocked
attempts/unknown fixture requests invalidate the run even if FastAPI converts an
exception into an HTTP 500. These process-wide guards are restored afterward;
**do not import/run this harness concurrently inside a production server**.

## Limits and review

These are real-clock, offline, in-process measurements with small fixed datasets.
They exclude Uvicorn/TCP/TLS, browser rendering, real provider variability,
internet latency, deployment resources and multi-worker coordination. App startup,
Python imports and fixture preparation are outside the per-request timings; first
artifact loading/parsing performed by a request is included. OS filesystem caches,
thread pools and imported libraries can remain warm between app instances.
Model first-use timing is therefore not a fresh-process cold-start measurement.

Provider delays and health gates are deliberately artificial. Do not treat these
numbers as production latency guarantees, compare different configurations as
equivalent, or add fragile wall-clock thresholds to CI. Review repeatable provider
counts, error rates and overlap first, then compare latency distributions on the
same machine/configuration before proposing a production optimization.

Run the focused offline regression suite with:

```bash
uv run --offline --project apps/api pytest apps/api/tests/test_benchmark_api.py -q
```

Tests cover real routes, observed concurrency, health overlap, fixture provenance,
cold/warm cache counts, missing artifacts, provider failures, percentile math,
network escape attempts, timeout cleanup, CLI bounds and JSON non-overwrite.
Run the repository lint, typecheck, test and build checks before review.
